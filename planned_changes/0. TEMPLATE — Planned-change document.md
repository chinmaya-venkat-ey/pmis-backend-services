## File-organization notes

- **Filename**: `N. <Title>.md` where `N` is the next integer in
  sequence. Don't reuse numbers — gaps and out-of-order numbers
  (e.g. `17a` exists alongside `17`) are tolerated for follow-up
  patches but new top-level docs start with the next free number.
- **Title in body**: matches the filename's title.
- **No emoji** in filenames or titles unless explicitly requested.
- **Commit message** when shipping: `Doc N: <one-line summary>`. Keep
  it informative — it's how `git log` becomes a useful audit trail.

## Cross-repo doc references

When a change spans multiple repos, the cross-cutting design lives
in the monolith's `planned_changes/`. Convention:

- **Pure project-management mirror** (project / M-A-T-S / activity-
  resource / dashboard / vendor catalogue work that mirrors monolith
  behaviour into this service) → doc lives in this repo.
- **Cross-cutting** (proxy plumbing, schema changes on shared
  tables, permission-code additions referenced by both services) →
  cross-cutting plan lives in `PMIS-OpenProject/planned_changes/`,
  and this repo carries a local repo-scoped slice that links back to
  the monolith doc by relative path.

**Numbering is per-repo and local.** Each repo numbers its own
planned-change docs `1, 2, 3, …` in the chronological order they were
authored *for that repo*, independent of every other repo. Doc 5 in
this repo has no relationship to doc 5 in monolith. Cross-repo
references use the file path (`../../PMIS-OpenProject/planned_changes/
38. ...md`) or the topic, never a bare doc number.

This service was extracted from the monolith and is currently
operated mostly as a mirror — most planned changes here are
back-ports / parity work driven by a monolith doc. That's fine and
expected.
