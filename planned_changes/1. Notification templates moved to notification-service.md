# Doc 1 — Notification templates moved out of this service

> Repo-scoped slice of monolith [doc 38](../../PMIS-OpenProject/planned_changes/38.%20Master%20endpoint%20ownership%20split%20%E2%80%94%20user-service%20vs%20notification-service.md). The cross-cutting plan + sequencing lives in monolith doc 38; this file is the user-service-specific change list.

This service stops being authoritative for `notification_templates`. The table, the model, the master endpoints, the local renderer — all gone. When user-service needs to send a notification (login OTP, password reset link/code), it POSTs `template_kind + payload` to the notification-service, which renders + dispatches.

---

## What this service loses

### Files deleted

- `app/api/v3/master_data/routes.py` — the notification-template CRUD endpoint block (6 endpoints + projector + the `_find_active_template` helper).
- `app/api/v3/master_data/schemas.py` — `NotificationTemplateCreateRequest`, `NotificationTemplateUpdateRequest`, `_validate_placeholder_set` helper, the `_ALLOWED_PLACEHOLDERS` registry. (The placeholder validator is reborn in notification-service.)
- `app/infrastructure/db/models/notification_template.py` — model gone. The TABLE remains in shared Postgres (notification-service owns it now).
- `tests/test_doc36_notification_templates.py` (if it was ported here) — coverage moves to notification-service.

### Files modified

- `app/infrastructure/db/models/__init__.py` — drop the `NotificationTemplateModel` import + entry from `__all__`.
- `app/infrastructure/db/session.py` — remove the notification-template seed loop. The bootstrap admin + RBAC seeds stay.
- `app/shared/notifications.py` — refactored:
  - `_lookup_template`, `_render_email`, `_render_sms`, `_compute_placeholders`, `_safe_format`, `_SafeDict`: **all deleted**.
  - `HttpNotificationClient.send` no longer renders. It POSTs `{to_recipient, template_kind, payload}` to notification-service's `/api/v1/notifications/{email,sms}/send` endpoint. Notification-service does the lookup + render + dispatch in one round-trip.
  - `MockNotificationClient.send` unchanged — still writes a `notification_log` row with the raw `payload` (no rendered output). For tests that assert specific rendered text, mock the notification-service HTTP call instead of relying on local rendering.
- `tests/conftest.py` — drop the autouse `_seed_notification_templates` fixture. Tests that need template-rendered content mock `httpx.Client` calls to notification-service.

### Postman collection

Drop the 6 notification-template entries from `PMIS_User_Service.postman_collection.json` Master Data folder. They live in the notification-service's own Postman collection now.

---

## What changes for callers

### user-service auth flows

`POST /users/login/send-otp`, `POST /users/login/verify-otp`, `POST /users/forgot-password`, `POST /users/reset-password`: behavior unchanged from the FE perspective. Internally, the dispatch goes through one extra HTTP hop:

```
Before:
  user-service ──renders locally──> POST /api/v1/notifications/email/send  (notification-service)
                                     {to, subject, body, is_html}

After:
  user-service ──>  POST /api/v1/notifications/email/send  (notification-service)
                    {to, template_kind, payload}
                    ──renders here──> dispatches via SMTP/SendGrid
```

### Master endpoint moves

| Path | Pre-doc-38 | Post-doc-38 |
|---|---|---|
| `/api/v3/master/notification_templates` | proxied here from monolith | proxied to notification-service from monolith |
| `/api/v3/master/notification_templates/{id}` | here | notification-service |
| `/api/v3/master/notification_templates/create` | here | notification-service |
| `/api/v3/master/notification_templates/{id}/restore` | here | notification-service |

(`/api/v3/master/roles` and `/api/v3/master/permissions` stay here — unchanged.)

---

## Migration / DB

Pre-doc-38 the `notification_templates` table was created by monolith doc-36's alembic migration (`c2d4e7f9a1b3`). The TABLE is unchanged; only the OWNERSHIP shifts. No new migration needed in this repo.

User-service's models still need `notification_log`, `otp_codes`, `password_reset_tokens` — those tables are user-service-domain (audit + auth state) and stay here.

---

## Test impact

Tests that previously hit user-service's `/api/v3/master/notification_templates/*` endpoints:

- If they were exercising the CRUD contract, they belong in notification-service now (port them).
- If they were just seeding test templates so the renderer wouldn't fall back, they need a different setup — mock `httpx.Client.post` for the notification-service URL.

The autouse fixture `_seed_notification_templates` in `tests/conftest.py` was a convenience for the second case. Delete it. Replace with mocks where needed.

---

## Cutover sequence (per monolith doc 38)

This change must land **after** notification-service has the templates + endpoints. The monolith proxy must keep pointing `/master/notification_templates` at user-service until notification-service is ready.

Order:

1. Notification-service: ship its planned-changes doc 1 (DB, model, master endpoints, render-and-dispatch shape on the existing /api/v1 dispatch routes).
2. **This repo**: ship this doc — drop the model, drop the master endpoints, simplify `HttpNotificationClient`, drop the seed fixture.
3. Monolith: split `_PROXIED_PATH_PREFIXES` and add `NotificationServiceProxyMiddleware`. Ship monolith doc 38.
4. Operationally: flip `NOTIFICATION_SERVICE_PROXY_ENABLED=true` on the monolith.

---

## Risks

- **Deploy ordering**: this repo's deploy must NOT precede notification-service's. If user-service ships first, the auth flows break (no local renderer + no notification-service templates). Recommended: joint deploy of notification-service + user-service in the same release.
- **Test flakiness**: tests that assert rendered output now depend on either real notification-service responses or mocked HTTP calls. Mock setup is a one-time cost; once landed, less brittle than the seed-based approach.
