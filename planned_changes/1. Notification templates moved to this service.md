# Doc 1 — Notification templates moved to this service

> Repo-scoped slice of monolith [doc 38](../../PMIS-OpenProject/planned_changes/38.%20Master%20endpoint%20ownership%20split%20%E2%80%94%20user-service%20vs%20notification-service.md). The cross-cutting plan + sequencing lives in monolith doc 38; this file is the notification-service-specific change list.

This service was a stateless dispatcher pre-doc-38. This change adds:

- A database (shared Postgres with monolith + user-service).
- Ownership of `notification_templates` (table, master endpoints, server-side rendering).
- JWT auth middleware on `/api/v3/master/*` endpoints (shared `SECRET_KEY`).
- A new optional shape on `/api/v1/notifications/email/send` and `/sms/send` that accepts `template_kind + payload` and renders server-side.

The legacy unauthenticated dispatch endpoints with pre-rendered `subject + body` keep working for back-compat.

### Schema (templated dispatch)

`/api/v1/notifications/email/send` accepts EITHER shape:

```json
// Legacy (unchanged)
{
  "to": ["user@example.com"],
  "subject": "Hello",
  "body": "<p>Hi</p>",
  "is_html": true,
  "cc": [],
  "bcc": []
}

// Doc 38 (new)
{
  "to": ["user@example.com"],
  "template_kind": "otp_login",
  "payload": {"code": "123456", "ttl_seconds": 300}
}
```

Service-layer rule: exactly one of `(subject + body)` or `template_kind` must be supplied. Mixing the two returns 422.

`/api/v1/notifications/sms/send` follows the same pattern.

## RBAC integration

`/api/v3/master/notification_templates/*` endpoints require:

- `Authorization: Bearer <jwt>` from a user authenticated by user-service.
- `master_data:view` permission for reads, `master_data:manage` for writes.

The auth middleware decodes the JWT (HS256 with shared `SECRET_KEY`), looks up the user's effective permission set via `RbacReadRepository.effective_permissions_for_user(user_id)` against the shared Postgres, and gates the route with the standard `require_permission(...)` dependency.

User-service is the AUTHORITATIVE writer for `users` / `roles` / `permissions` / `role_permissions` / `user_roles` / `user_permissions`. This service only reads.

## Database

The `notification_templates` table is created by monolith's `c2d4e7f9a1b3` alembic revision (doc 36). Doc 38 doesn't change schema — only ownership.

For local dev with SQLite:

```bash
# Create tables in-process (no alembic)
python -c "from app.db.session import Base, engine; from app.db.models import notification_template; Base.metadata.create_all(bind=engine)"
```

For shared-Postgres deploys: `MIGRATIONS_AUTORUN=false`. Monolith owns alembic; this service expects the schema to be at head.

### Seeding

`init_db` (called from `app/main.py` lifespan) seeds 6 built-in template rows on first boot:

- `otp_login` × `email`
- `otp_login` × `sms`
- `password_reset_link` × `email`
- `password_reset_link` × `sms`
- `password_reset_otp` × `email`
- `password_reset_otp` × `sms`

Same content user-service used to seed. Idempotent — only inserts missing rows; preserves edits across boots.

## Render-and-dispatch flow (the new internal contract)

```
Caller (user-service or monolith) -->  POST /api/v1/notifications/email/send
                                       {to, template_kind="otp_login", payload={code:..., ttl_seconds:300}}
                                          │
                                          ▼
                                    EmailController
                                          │
                                          ▼
                                    EmailService.send_email(payload)
                                          │
                                          ▼ (template_kind set?)
                                    template_service.render_email(db, kind, payload)
                                       1. lookup active row in notification_templates
                                          WHERE template_kind=kind AND channel='email'
                                       2. _compute_placeholders(kind, payload)
                                          - {code}, {ttl_minutes}      (otp / reset_otp)
                                          - {reset_url}, {token}, ...  (reset_link)
                                       3. row.body.format_map(_SafeDict(placeholders))
                                       4. fallback to generic body when no row found
                                          │
                                          ▼ (subject, body, is_html)
                                    EmailService.dispatch via SMTP / SendGrid
                                          │
                                          ▼
                                    Response: {success, message_id, ...}
```

Same renderer logic that previously lived in user-service's `app/shared/notifications.py` — moved here verbatim, plus the helper functions (`_safe_format`, `_SafeDict`, `_compute_placeholders`) and the placeholder allow-list.

## Configuration

New env vars:

```bash
# Database (shared Postgres)
DATABASE_URL=postgresql://user:pass@host:5432/pmis
MIGRATIONS_AUTORUN=false
MIGRATIONS_REQUIRED=true

# Auth (shared with monolith + user-service)
SECRET_KEY=<32+ chars; identical to monolith>
ALGORITHM=HS256

# Template rendering
FRONTEND_BASE_URL=                  # used in password-reset email links; fallback to bare-token rendering when blank
```

Existing email/sms provider env vars (smtp_*, sendgrid_*, twilio_*, msg91_*) unchanged.
