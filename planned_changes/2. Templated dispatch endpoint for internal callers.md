# 2. Templated dispatch endpoint for internal callers

## Why

Doc 38 phase 1 moved the `notification_templates` master catalog to this service, but user-mgmt was still rendering templates locally before calling `/email/send` and `/sms/send`. That meant:

- Two services held copies of the same template catalog (notification-service + user-mgmt's local DB).
- Render logic was duplicated — `_render_email`, `_render_sms`, placeholder computation, fallback strings — in both services.
- Updating a template required updating two seed loops + two pieces of code that read them.

Doc 38 phase 2 collapses that. user-mgmt becomes a thin client that posts the dispatch intent and lets this service do the lookup + render + dispatch.

## What

A single new route plus its schemas, registered alongside the existing `/email/send`, `/sms/send`, `/otp/send` endpoints under `/api/v1/notifications/`.

| File | Change |
| --- | --- |
| `app/schemas/dispatch.py` | New. `DispatchRequest` (`channel: Literal["email","sms"]`, `recipient`, `template_kind`, `payload`, optional `user_id`) and `DispatchResponse` (`success`, `message`, `provider`, `message_id`, `channel`, `template_kind`, optional `rendered_subject`). |
| `app/routes/dispatch_routes.py` | New. `POST /api/v1/notifications/dispatch`. Calls `template_service.render_email` / `render_sms`, then `EmailService.send` / `SMSService.send`, returns the merged result. |
| `app/routes/__init__.py` | Includes the new router under the existing `/api/v1` prefix. |
| `tests/test_dispatch.py` | New. 5 tests: email render via seeded template, sms render via seeded template, fallback when template missing, unknown channel rejected, missing fields rejected. |

## What stays the same

- `/email/send` and `/sms/send` are unchanged. Callers that already render their own subject/body keep working.
- `/api/v3/master/notification_templates/*` is unchanged.
- Auth posture: `/dispatch` is unauthenticated (internal-network only), matching its siblings. See [points_to_consider/dispatch-endpoint-internal-network-only.md](../points_to_consider/dispatch-endpoint-internal-network-only.md).
- Provider selection (`EMAIL_PROVIDER`, `SMS_PROVIDER`) — same env knobs.

## Wire shape

Request:

```json
POST /api/v1/notifications/dispatch
{
  "channel": "email",
  "recipient": "alice@example.com",
  "template_kind": "otp_login",
  "payload": {"code": "123456", "ttl_seconds": 300},
  "user_id": "uuid-or-null"
}
```

Response:

```json
{
  "success": true,
  "message": "Email sent successfully",
  "provider": "smtp",
  "message_id": "smtp-...",
  "channel": "email",
  "template_kind": "otp_login",
  "rendered_subject": "Your PMIS login verification code"
}
```

`rendered_subject` is omitted for SMS.

## Failure modes

- **Template missing for the requested kind/channel** → `render_email`/`render_sms` returns the fallback subject + body and the dispatch proceeds with `provider`/`message_id` populated. Logs a warning. Never 5xx.
- **Provider unreachable** (e.g. SMTP refused) → `EmailService.send` raises `HTTPException(502)`; the response body carries the provider error message.
- **Unknown channel** → 422 (Pydantic `Literal` validation).
- **Missing fields** → 422 (Pydantic field validation).

## Verification

Smoke test (run during commit `9e28f20`) with all 3 services running, shared-DB topology:

- `POST /api/v1/notifications/dispatch` with sms + mock provider → `{success: true, channel: "sms", template_kind: "otp_login", message_id: "mock-..."}`.
- `POST /api/v1/notifications/dispatch` with email + unreachable SMTP → 502 with provider error in body, no crash.
- End-to-end: user-mgmt's `/api/v3/users/forgot-password` → user-mgmt's `HttpNotificationClient.send` → `/api/v1/notifications/dispatch` → mock SMS → audit row in user-mgmt's `notification_log` written with `status="sent"` and `_dispatch.provider="mock"`.

Unit tests: 26 passing in this repo (21 prior + 5 new dispatch tests).
