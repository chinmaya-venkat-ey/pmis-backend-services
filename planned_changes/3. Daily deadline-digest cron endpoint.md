# Doc 3 — Daily deadline-digest cron endpoint

> **Status: SHIPPED-PENDING-DEPLOY** — code landed on `dev`; awaiting
> the DevOps host cron to be wired to call the endpoint.
>
> Cross-cutting design lives in
> [`PMIS-OpenProject/planned_changes/51. Daily deadline-digest cron.md`](../../PMIS-OpenProject/planned_changes/51.%20Daily%20deadline-digest%20cron.md).
> This file is the notification-service-specific slice.

A new endpoint that DevOps's system cron curls once a day. The
endpoint scans the shared `pmis_db` for milestones / activities ending
in the next few days (or already past due), groups them per
responsible user (org-admin / project-admin / project-member scoped
to the project), and sends one email per user via the existing
`email_service`. No new email plumbing — reuses the dispatch pipeline.

| # | Sub-change |
|---|------------|
| 1 | New endpoint `POST /api/v1/notifications/cron/daily-digest` gated by `X-Cron-Secret` header. |
| 2 | New service module `app/services/digest_service.py` — scan + recipient resolution + per-user aggregation + render + send. |
| 3 | New built-in template `project_deadline_digest` (email, HTML, subdued styling). |
| 4 | Six new read-only ORM mirrors (`projects`, `milestones`, `activities`, `users`, `roles`, `user_role_assignments`, `project_vendors`) so the digest can join the shared schema without an HTTP hop. |

---

## Why this exists

Project work has deadlines; the system has all the data; humans have
been finding out about overdue items in stand-ups instead of email.
Daily digest plugs the gap without spamming — one email per user per
day, covering everything they care about.

The scope is deliberately small for v1: no notifications outside the
deadline-digest pattern, no in-app inbox, no preference toggles. If
the digest is too noisy or not noisy enough we'll tune the window
and add filters in a follow-up doc.

## What's in scope / out of scope

- ✅ Daily digest by host cron — one POST a day
- ✅ Recipients: org_admin / project_admin / project_member scoped
  to each affected project
- ✅ Items: milestones + activities whose `end_date` is within
  `DEADLINE_WINDOW_DAYS` (default 5) OR already past due
- ✅ Skip rules: completed items, closed / soft-deleted projects,
  soft-deleted / non-active users, users with no email
- ✅ De-dupe: a user holding multiple qualifying roles on the same
  project still sees each item once
- ✅ Email-from / SMTP / SendGrid: reuses existing notification-
  service config
- ❌ Tasks / subtasks — not included in v1 (milestones + activities
  only)
- ❌ Per-user preferences (opt-out, quiet hours) — would need a new
  table; defer
- ❌ In-app notifications — out of scope
- ❌ SMS digest — out of scope (email-only template)
- ❌ Deduplication across days (so a 5-day-out item triggers a fresh
  email every day until it's done) — that's the design, not a bug.
  If it ever gets noisy we add per-user-per-day-sent state.

## Decision log

| Q | Decision | Rationale |
|---|---|---|
| Where does the cron logic live? | notification-service | Already has dispatch + SMTP + template rendering + `notification_log` audit. Project-mgmt would have to call back to notification-service anyway — extra hop for no gain. Shared DB means notification-service can run the queries directly. |
| Cron mechanism | DevOps host cron + POST endpoint, NOT an in-app scheduler | Per user instruction. Avoids new container, simpler ops, easier to replay (just curl). |
| Endpoint auth | Shared-secret header `X-Cron-Secret` matching `CRON_SHARED_SECRET` env | Simpler than minting a service JWT. The endpoint never touches user-bearer flows so SECRET_KEY isn't relevant. |
| Empty secret behaviour | Endpoint returns 503 | Boot-safe default — endpoint is "disabled" until ops explicitly sets the env var. |
| ORM mirrors vs raw SQL | Read-only ORM mirrors | Matches user-mgmt's `DivisionModel` mirror precedent. Tests can `Base.metadata.create_all` the mirrors in in-memory SQLite without monolith's full schema. |
| Template engine | `str.format_map` (existing) with pre-rendered `items_html` | Reuses the renderer. Loops in templates would mean Jinja2 — bigger lift, not justified for one new template. |
| Empty-digest behaviour | No email sent at all (skip) | Avoid spamming users who happen to have no due items today. |

## API surface

### New endpoint

| Method | Path | Auth | Notes |
|--------|------|------|-------|
| POST | `/api/v1/notifications/cron/daily-digest` | `X-Cron-Secret` header | Body is optional. Returns a summary of what the run did. |

Request body (all fields optional):

```json
{
  "today": "2026-05-12",       // ISO date — overrides the cron's notion of 'today'
  "windowDays": 5              // override DEADLINE_WINDOW_DAYS for this call
}
```

Response:

```json
{
  "ranAt": "2026-05-12T09:00:00+05:30",
  "usersNotified": 14,
  "emailsSent": 14,
  "emailsFailed": 0,
  "itemsAggregated": 47
}
```

Error responses:
- `401` — missing or wrong `X-Cron-Secret`
- `503` — `CRON_SHARED_SECRET` env var not configured (endpoint disabled)

## Schema

No schema change to existing tables. The new read-only models declare
the columns this service queries. In production the tables already
exist (monolith owns them); `Base.metadata.create_all` is a no-op on
shared-DB deploys.

Mirrors added in `app/db/models/`:
- `project.py` — `id, project_code, name, status, deleted_at`
- `milestone.py` — `id, project_id, name, start_date, end_date, status, deleted_at`
- `activity.py` — `id, project_id, milestone_id, name, start_date, end_date, status, deleted_at`
- `user.py` — `id, login, email, first_name, last_name, status, deleted_at`
- `role.py` — `id, name`
- `user_role_assignment.py` — `id, user_id, role_id, organization_id, project_id`
- `project_vendor.py` — `project_id, vendor_id`

## New template

```
template_kind   = project_deadline_digest
channel         = email
subject         = "PMIS — upcoming deadlines on your projects"
is_html         = true
placeholders    = {first_name}, {items_html}, {portal_url}
```

Body kept subdued — no warning colours, no exclamation marks, normal
font sizes. Each project block is `<b>{Name}</b> ({CODE})` followed
by a flat `<ul>` of items. Past-due items just read "past due by N
days" inline.

`items_html` is pre-rendered by `digest_service.render_items_html`
before dispatch (since `str.format_map` can't loop).

`portal_url` comes from `FRONTEND_BASE_URL` — same env var the
password-reset emails already use.

The placeholder allow-list in `app/schemas/notification_template.py`
was extended to include this kind so admins can edit it via the
existing master-data UI without the placeholder validator rejecting
the saved body.

## Service-layer rules

In `app/services/digest_service.py`:

- `find_due_milestones(db, today, window_days)` and
  `find_due_activities(db, today, window_days)` return rows whose
  `end_date < (today + window_days + 1)` AND
  parent project is `status != 'closed'` AND `deleted_at IS NULL` AND
  row itself is `deleted_at IS NULL` AND row's status `!= 'completed'`.
  Overdue rows (end_date < today) are included by construction.
- `responsible_user_ids(db, project_id)` returns distinct active user
  ids holding one of `(org_admin, project_admin, project_member)`
  scoped either to the project (via `project_id`) or to a vendor the
  project is mapped to (via `organization_id` + `project_vendors`).
- `aggregate_by_user(db, today, window_days)` walks the discovery
  results, resolves recipients per project, and de-dupes per user.
- `run_daily_digest(db, email_service, today, window_days)` is the
  orchestrator the endpoint calls — renders + sends per user, returns
  a `DigestSummary`.

## Cutover / rollout

### Dev / staging
1. Set `CRON_SHARED_SECRET=<long-random-string>` on the
   notification-service container.
2. Set `FRONTEND_BASE_URL=https://pmis-dev.example/` (or whatever
   the dev portal URL is) — same env var the password-reset email
   already uses.
3. Restart `pmis-notification`.
4. Smoke-test: `curl -X POST -H "X-Cron-Secret: …"
   https://<host>:8002/api/v1/notifications/cron/daily-digest` —
   expect a JSON summary with counts.
5. Inspect `notification_log` to confirm rows for the sent emails.

### Production
- DevOps wires the host crontab to call the endpoint daily at the
  agreed time (suggested: 09:00 IST).
- Suggested entry: `0 9 * * * curl -fsS -X POST -H "X-Cron-Secret: $SECRET" http://localhost:8002/api/v1/notifications/cron/daily-digest > /var/log/pmis/daily-digest.json`

### Rollback
- Unset `CRON_SHARED_SECRET` (or set it to empty) — the endpoint
  starts returning 503, the cron caller logs an error, no emails
  go out.
- Optionally: deactivate the `project_deadline_digest` template row
  via the master-data UI — the renderer falls through to the
  generic fallback, which is harmless.

## Risks + open questions

- **Email noise** — if a project has many milestones / activities,
  each user gets one block per project per day. Mitigated by the
  per-project grouping in the HTML, but worth watching once
  deployed. If it's too much, the natural follow-up is to cap items
  per user or shift to weekly + opt-in daily.
- **Time-zone handling** — `today` is computed in UTC. The window
  comparison uses naive datetimes against the DB (matches the rest
  of PMIS). For an IST-centric deployment this can mean the cron
  fires "today" slightly differently than a human-IST "today" if
  run at the IST/UTC boundary. The endpoint accepts an explicit
  `today` override so DevOps can pin it.
- **SMTP / SendGrid outage** — each failed `email_service.send`
  is logged but doesn't abort the run. Next-day's run will re-send.
- **Recipient overreach** — if an org_admin is mapped to a vendor
  that owns many projects, they'll see all of them in one digest.
  By design.
