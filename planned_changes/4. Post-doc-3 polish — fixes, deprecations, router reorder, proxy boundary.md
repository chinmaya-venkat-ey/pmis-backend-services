## Why this exists

Doc 41 was a substantial RBAC refactor. The first deploy hit production,
the role matrix passed 65/65 against the live server, but the live
walkthrough surfaced two non-doc-41 bugs (notification URL + a
spec-alignment slip in `project_admin`'s seed) and several hygiene
items (CORS ordering parity with monolith, OpenAPI deprecation
markers, Swagger UI's tag order). Each is too small to merit its own
plan doc, and they're all tied to the doc-41 work — so they get one
shared doc 42.

The last item (proxy boundary) needs its own paragraph: the new
doc-41 endpoints under `/projects/{id}/role-assignments` and
`/vendors/{id}/projects` could in principle be proxied through monolith
on `:8000` to keep the FE on a single base URL. We chose **not** to —
those URLs share namespaces (`/projects/*`, `/vendors/*`) that monolith
owns its own routers for, and proxying them would either drag in
unrelated routes or shadow legacy handlers. The decision is
documented here so future maintainers don't try to "fix" the apparent
gap.

## 1. Notification-service URL fix (config-only)

**Symptom**: every authenticated login that needed an OTP showed up in
`notification_log` with `status='failed'` and
`error: ConnectError: [Errno 111] Connection refused`. Universal OTP
(`000000`) was masking the broken email path so login still worked
in tests, but real users would never receive an OTP email.

**Root cause**: `pmis-usermanagement/.env` had
`NOTIFICATION_SERVICE_URL=http://127.0.0.1:8002`. Inside the user-mgmt
container that loops back to the container itself, not the host —
the notification service runs on the host's port 8002.

**Fix**: changed to `NOTIFICATION_SERVICE_URL=http://host.docker.internal:8002`
in `/home/uidaiadmin/pmis-usermanagement/.env`, recreated the container.
The previous value was kept as a `.env.bak.<timestamp>` (later removed
during cleanup).

**Verification**: chinmay-test login → `notification_log` row with
`status='sent'`, `error=NULL`. The user confirmed the OTP arrived
in their real inbox.

This was applied directly on the deploy host because:
- It's environment-specific config, not source-tree-tracked.
- The committed `.env.example` files in both repos already document
  `host.docker.internal` as the expected value for containerised
  deploys.

**Follow-up**: a CI lint that flags any `*_SERVICE_URL` env var
pointing at `127.0.0.1` or `localhost` inside a Docker-compose
service that does NOT use `network_mode: host`. Not done in this doc.

## 2. `project_admin` permission seed trim

**Symptom**: the doc-41 role-permission matrix passed 65/65, but a
read-through of the seed list revealed `MILESTONES_UPDATE` and
`ACTIVITIES_UPDATE` were granted to `project_admin`. The lead's
spec for the role was "manage task and sub-task and add project
member" — milestones and activities are navigation anchors, not
edit targets, for the role.

**Fix**:
- Code change in both repos' `app/core/permissions.py`:
  `PROJECT_ADMIN_ROLE_PERMISSIONS` no longer carries
  `MILESTONES_UPDATE` / `ACTIVITIES_UPDATE`. user-mgmt commit
  `38c74e6`, monolith commit `361ac98`.
- Live DB revoke (since `sync_builtin_permissions` only seeds when
  the role's permission set is empty — won't revoke on its own):
  ```sql
  DELETE FROM role_permissions
   WHERE role_id = (SELECT id FROM roles WHERE name='project_admin')
     AND permission_code IN ('milestones:update', 'activities:update');
  ```
  2 rows deleted.

**Verification**: a `project_admin`-scoped test user PATCHing a
milestone or activity now gets a clean 403 with the explicit gate
message `"Insufficient permissions. Required: milestones:update on
project ..."`. Tasks/subtasks writes still pass through unchanged.

## 3. `CORSMiddleware` reorder in user-mgmt

**Symptom**: caught during the post-deploy middleware audit. user-mgmt's
`app/main.py` added `CORSMiddleware` FIRST → INNERMOST in Starlette's
LIFO wrap. Practically OK on the happy path (auth doesn't raise on
invalid tokens, no proxy short-circuit), but fragile: any future
middleware that short-circuits a response above CORS would strip
`Access-Control-Allow-*` headers and the browser would block the
response with "failed to fetch" — the same failure mode the monolith
fixed in doc 39.

**Fix** (commit `4003461`): reordered so `CORSMiddleware` is added
LAST → OUTERMOST. Final order:

```
Request flow:
  CORSMiddleware (outermost)
    → AuthenticationMiddleware
      → LoggingMiddleware (innermost)
        → route handler
```

**Verification**: OPTIONS preflight + actual request both return
`access-control-allow-origin` + `access-control-allow-credentials`
headers; OPTIONS short-circuits at CORS without traversing
auth/logging.

## 4. Deprecation markers on legacy `/users/{id}/roles*`

**Symptom**: a survey of the role/permission endpoint surface showed
that `/api/v3/users/{id}/roles[/{role_id}]` (legacy global) had no
deprecation indication anywhere — no `Deprecation` header, no
"DEPRECATED" prefix in the OpenAPI summary, no description warning.
But doc 41 explicitly superseded it with `/role-assignments`.

**Fix** (commit `0e394d6`): on all three legacy endpoints
(`GET /users/{id}/roles`, `POST /users/{id}/roles/{role_id}`,
`DELETE /users/{id}/roles/{role_id}`):

- OpenAPI summary line stamped `(DEPRECATED — use ... /role-assignments ...)`.
- OpenAPI description field expanded with what the deprecation means
  + which endpoint to migrate to.
- Response body wrapped in `BaseController.stamp_deprecation()` so
  every response carries `Deprecation: true` +
  `Link: </api/v3/users/{id}/role-assignments>; rel="successor-version"`.

The legacy `/api/v3/roles/*` and `/api/v3/permissions/*` catalog
endpoints already had this pattern via the doc-21B work — the
post-doc-41 audit just brought the user-side legacy routes to parity.

## 5. Router include-order tidy

**Symptom**: FastAPI's Swagger UI groups endpoints by tag in router
include order. Before this change, the deprecated `/roles` and
`/permissions` tags appeared near the top of `/docs` in user-mgmt,
mixed in with the canonical `/users` and `/master`. Same layout
issue in monolith — `project_members`, `roles`, `permissions`,
`work_packages*`, `meetings*` were scattered between the active
surfaces.

**Fix**:

| Repo | Commit | What |
|---|---|---|
| user-mgmt | `5a46ee1` | Reorder: `users → master_data → role_assignments (×3 doc-41) → roles (DEPRECATED) → permissions (DEPRECATED)`. |
| monolith | `e08333d` | Reorder: active routers (users, projects, M/A/T/S, tree, vendors, resource_types, catalogs, master_data, comments, attachments) at the top; legacy / superseded routers (project_members, roles, permissions, work_packages*, meetings*) at the bottom. |

No behaviour change — pure Swagger UI cosmetics. master_data router
position preserved (per "don't disturb masters" guidance).

## 6. Proxy boundary lock — doc-41 project/vendor variants stay on `:8001`

**Decision**: monolith's `UserServiceProxyMiddleware` does NOT forward
the new doc-41 project- and vendor-side endpoints. FE integrates
against user-mgmt `:8001` directly for those.

**What's still proxied** (unchanged from doc 37 part 2):
- `/api/v3/users/*` → forwards to user-mgmt. Includes the doc-41
  user-side variants (`/users/{id}/role-assignments`,
  `/users/{id}/projects`) by way of the existing `/users/*` prefix.
- `/api/v3/master/roles/*` → forwards.
- `/api/v3/master/permissions/*` → forwards.

**What's NOT proxied** (this doc's decision):
- `/api/v3/projects/{id}/role-assignments` — calls via `:8000` return
  404; calls via `:8001` return the doc-41 response.
- `/api/v3/vendors/{id}/projects` — calls via `:8000` hit monolith's
  pre-existing legacy handler (different shape, no `roleAssignments`);
  calls via `:8001` return the doc-41 response with
  `?expand=role-assignments` support.

**Rationale**: those URLs sit inside `/projects/*` and `/vendors/*`
namespaces that monolith owns. Blanket-proxying either prefix would
forward dozens of unrelated routes. Adding regex pattern matching to
the proxy was prototyped (a `_PROXIED_PATH_PATTERNS` list with two
regexes) but reverted at the user's explicit request: the new
endpoints are not yet integrated by any FE caller, so it makes more
sense to keep the proxy surface minimal and have the FE talk to
`:8001` directly. This also reduces the user-mgmt service's
dependency on monolith.

**Test** (`tests/test_doc37_user_service_proxy.py`):

- `test_doc41_project_role_assignments_NOT_proxied` — asserts the
  matcher returns False for `/api/v3/projects/{id}/role-assignments`.
- `test_doc41_vendor_projects_NOT_proxied` — same for vendor variant.
- `test_users_role_assignments_IS_proxied_via_users_prefix` —
  asserts the user-side variant DOES proxy via the existing rule.
