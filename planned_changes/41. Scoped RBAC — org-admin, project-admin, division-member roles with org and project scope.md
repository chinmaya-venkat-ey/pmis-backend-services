Today's RBAC is **flat / global**: a user's roles (via `user_roles`) and
direct grants (via `user_permissions`) apply across the whole product.
There is no notion of "X is admin _of project P_" or "Y is admin _of
vendor/organization V_" — every grant is universal.

The lead has asked for a real scoped model: **`Users → Roles →
Permissions, with a Scope (Org or Project) on each assignment`**. Three
new role buckets land alongside the existing `admin` / `member` /
`viewer` / `vendor` seed:

| # | Sub-change |
|---|---|
| 1 | Add a `user_role_assignments` table carrying `(user_id, role_id, organization_id?, project_id?)` and migrate rows from `user_roles` + `project_members.roles[]` into it. |
| 2 | Seed five new roles: `super_admin`, `admin`, `org_admin`, `project_admin`, `project_member`, `division_member`. (Existing `member`/`viewer`/`vendor` roles stay; see Decision Log Q-A.) |
| 3 | Make permission checks scope-aware: `require_permission(code)` keeps working for global gates; `require_project_permission(code)` (new) honours the project_id in the path; `require_org_permission(code)` (new) honours the caller's org. |
| 4 | Add new permission codes for the workflow gates the role spec implies (`USERS_GRANT_SUPERADMIN`, `ACTIVITIES_REQUEST_STATUS_CHANGE`, `ACTIVITIES_APPROVE_STATUS_CHANGE`). |
| 5 | Add user-management API surface for **assigning scoped roles**: `POST /api/v3/users/{id}/role-assignments`, `GET /api/v3/users/{id}/role-assignments`, `DELETE /api/v3/users/{id}/role-assignments/{aid}`. |
| 6 | Add **project-mapping view endpoints** that power the User-Mgmt and Org-Mgmt menus (per the FE mock): `GET /api/v3/projects/{id}/role-assignments` (per-project drill-down), `GET /api/v3/vendors/{id}/projects` (Org Mgmt landing), `GET /api/v3/users/{id}/projects` (User Mgmt landing). All served by user-management. |

---

## Why this exists

The current single-role-per-user-globally model breaks down once we
have more than one tier of admin: an "org admin" who owns Vendor X
must NOT be able to edit projects belonging to Vendor Y; a "project
admin" of Project P must NOT be able to delete or publish projects
they aren't on. The flat RBAC also makes the new approval workflow
("division member can give / ask for approval on activity status
change") impossible to gate cleanly.

The lead's RBAC spec is the textbook fix: assignments carry their own
scope, and the runtime check unions "the user's role at this scope" +
"the user's role at the parent scope (org of project, etc.)" to decide.

## Decision log (proposed — pending Q1–Q4 in "Open questions" below)

| Q | Proposed decision | Rationale |
|---|---|---|
| A | "Vendor" IS the "Organization". | Today's `users.vendor_id` already names the user's owning entity. Adding a parallel `organizations` table would force two-way sync with vendors and add no real semantics. |
| B | New `user_role_assignments` table. `user_roles` stays as a thin alias view (or is dropped after migration; see Q2). | Adding `org_id` + `project_id` to the existing 2-col PK would force a schema rewrite and break every existing FK. A clean new table with PK `(id)` is simpler to roll out. |
| C | `require_permission(code)` is still the global check; `require_project_permission(code)` and `require_org_permission(code)` are new helpers that take the relevant scope from the path / the caller's vendor. | Routes that don't care about scope (catalog reads, master data) stay untouched. Only routes that *should* be scope-gated opt in. |
| D | `division_member` is project-scoped, with `user.division` driving the activity-side filter (an activity tagged `concerned_division=tmd1` is actionable only by division members on the project who hold `division=tmd1`). | Adding a third scope dimension materially complicates the assignment model for one role. Filtering by an existing user attribute is effectively the same with no schema cost. |
| E | "Admin (not super-admin)" role: same permission set as super-admin **minus** the new `USERS_GRANT_SUPERADMIN` code. | One permission code keeps the role surface narrow. Easier to audit than "two near-identical roles." |
| F | Effective-permission cache stays per-request, but is now `Dict[scope_key, Set[str]]` rather than a single Set. Scope key is `("global",)`, `("org", vendor_id)`, or `("project", project_id)`. The legacy "anywhere" Set is built by union-ing all values. | Old code paths (`require_permission`) keep using the union; new scoped checks consult the right bucket. One DB load per request, same query cost. |

## Schema (proposed)

```
user_role_assignments
  id                INTEGER PK autoincrement
  user_id           VARCHAR(36) NOT NULL  FK → users.id
  role_id           INTEGER     NOT NULL  FK → roles.id
  organization_id   VARCHAR(36) NULL      FK → vendors.id   (org scope)
  project_id        VARCHAR(36) NULL      FK → projects.id  (project scope)
  created_at        UtcDateTime NOT NULL
  created_by        VARCHAR(36) NULL      FK → users.id

  -- exactly-one scope:  (org_id IS NULL AND project_id IS NULL)        -> global
  --                    (org_id IS NOT NULL AND project_id IS NULL)    -> org-scoped
  --                    (org_id IS NULL AND project_id IS NOT NULL)    -> project-scoped
  CHECK ( NOT (organization_id IS NOT NULL AND project_id IS NOT NULL) )

  UNIQUE (user_id, role_id, organization_id, project_id)
  INDEX  (user_id)
  INDEX  (project_id)
  INDEX  (organization_id)

roles  (existing, unchanged)
  + 5 new seed rows: super_admin, org_admin, project_admin, project_member, division_member

permissions  (existing — additions only)
  + USERS_GRANT_SUPERADMIN              "Grant the super_admin role to a user."
  -- Activity status-change codes are NOT added here. They'll land
  -- alongside the workbox / approval feature in a future doc.

project_members  (existing, unchanged for this doc)
  -- The `roles` JSON column STAYS during the migration window.
  -- A backfill copies each row into user_role_assignments
  -- (project_id=that project, role_id=mapped from JSON contents).
  -- The column is dropped in a follow-up doc once monolith FE
  -- reads exclusively from user_role_assignments.
```

## API surface (user-mgmt only)

### New endpoints

**Assignment CRUD** (the action surface):

| Method | Path | Permission | Scope |
|--------|------|------------|-------|
| POST   | `/api/v3/users/{id}/role-assignments` | `RBAC_ASSIGN` | caller's grant ability is checked against the scope of the assignment they're creating |
| GET    | `/api/v3/users/{id}/role-assignments` | `USERS_READ` (own) / `USERS_READ_ALL` | — |
| DELETE | `/api/v3/users/{id}/role-assignments/{aid}` | `RBAC_ASSIGN` | same caller-scope check |
| POST   | `/api/v3/projects/{id}/role-assignments` | `RBAC_ASSIGN` | scope-checks against project's owning vendor |
| DELETE | `/api/v3/projects/{id}/role-assignments/{aid}` | `RBAC_ASSIGN` | same |

**Project-mapping read views** (the screenshot's tables — Q5):

| Method | Path | Permission | Returns |
|--------|------|------------|---------|
| GET    | `/api/v3/projects/{id}/role-assignments` | `PROJECT_MEMBERS_READ` | grouped: `[{role, users:[{id,login,email}]}]` — powers the per-project drill-down (UIDAI PMIS row in the mock) |
| GET    | `/api/v3/vendors/{id}/projects?expand=role-assignments` | `PROJECTS_READ_ALL` (or org_admin in scope) | `[{project, roleAssignments:[...]}]` — Org Mgmt menu landing |
| GET    | `/api/v3/users/{id}/projects?expand=role-assignments` | `USERS_READ` (own) / `USERS_READ_ALL` | `[{project, role}]` — User Mgmt menu landing |

All read views are served by user-management. The vendor↔project link
already exists in user-management via the `project_vendors` table
([app/infrastructure/db/models/project_vendor.py](PMIS-user-management/app/infrastructure/db/models/project_vendor.py))
so no monolith roundtrip.

### Caller-vs-target authorization rules

| Caller's role        | Can grant                                              |
|----------------------|--------------------------------------------------------|
| `super_admin`        | any role at any scope (only one who can grant `super_admin`) |
| `admin`              | any role except `super_admin`                          |
| `org_admin` (org X)  | `project_admin` / `project_member` / `division_member` on projects whose owning vendor = X |
| `project_admin` (P)  | `project_member` only, scoped to project P             |
| anyone else          | nothing                                                |

These rules are enforced in the assignment-create service, not in the
permission decorator (the decorator just gates `RBAC_ASSIGN` — the
caller-vs-target check is business logic). Tests cover every cell.

### Monolith touch surface (Q3 — scope enforcement bundled in)

Adding scope enforcement everywhere is a much bigger PR than just
"add the new table" — we need to be deliberate about which routes
get the new gate. The principle: **gate writes, leave reads on the
union**. Read paths in monolith already filter by project membership
at the repo layer, so the scope boundary on reads is already in
place; the leak is on writes.

**New helper (monolith)**: `app/core/middleware/rbac.py` gains:

```python
def require_project_permission(code: str):
    """Gate <code> on the project_id resolved from the request path.

    Resolves project_id from path_params in this priority order:
      1. project_uuid / project_id (direct)
      2. milestone_id   → milestones.project_id
      3. activity_id    → activities.project_id
      4. task_id        → activities → milestones.project_id
      5. subtask_id     → tasks → activities → milestones.project_id

    The user must hold <code> at scope ('project', project_id) OR
    at scope ('global',) — global perms still pass scoped checks.
    """
```

`require_org_permission(code)` follows the same pattern but resolves
`organization_id` from the project's owning vendor.

**Routes switched from `require_permission` → `require_project_permission`** (writes only):

| File | Routes | Code |
|---|---|---|
| `app/api/v3/projects/routes.py` | PATCH `/projects/{id}`, DELETE `/projects/{id}`, POST `/projects/{id}/publish`, POST `/projects/{id}/close` | `PROJECTS_UPDATE` / `PROJECTS_DELETE` / `PROJECTS_PUBLISH` / `PROJECTS_CLOSE` |
| `app/api/v3/milestones/routes.py` | POST/PATCH/DELETE | `MILESTONES_*` |
| `app/api/v3/activities/routes.py` | POST/PATCH/DELETE | `ACTIVITIES_*` |
| `app/api/v3/tasks/routes.py` | POST/PATCH/DELETE | `TASKS_*` |
| `app/api/v3/subtasks/routes.py` | POST/PATCH/DELETE | `SUBTASKS_*` |
| `app/api/v3/project_members/routes.py` | POST/PATCH/DELETE | `PROJECT_MEMBERS_*` |

**Routes intentionally LEFT on `require_permission` (the union path)
even though they're writes**:

- `app/api/v3/comments/*` — `POST /<target_kind>/{target_id}/comments`
  uses a generic `target_id` path param; the target_kind is implicit
  in the URL segment (`/milestones/...` vs `/tasks/...`). Scoping
  this cleanly requires either a target-kind-aware decorator
  factory or URL-string parsing in the resolver — both ugly. Left
  on the union for this doc; can be tightened in a follow-up.
- `app/api/v3/attachments/*` — same shape as comments. Same
  rationale.

**Routes left on `require_permission` (the union path)**:

- All read endpoints (`GET /projects`, `GET /projects/{id}`, `/tree`, etc.) — repo-layer membership filter is the existing scope boundary.
- Master-data endpoints (`/master/*`) — global by design.
- User-management surface in monolith — none, this lives in user-mgmt.
- Catalog endpoints (`/vendors`, `/divisions`, `/resource_types`) — global.

**Auth middleware change (both repos)**: `request.state.user_permissions`
gains a sibling `request.state.scoped_permissions: Dict[Tuple[str, str], Set[str]]`
keyed by `(scope_kind, scope_id)`. The legacy `user_permissions` Set
stays the **union of every scope** so existing `require_permission`
calls keep their semantics. The scoped-permission load is one query
per request — JOIN of `user_role_assignments + role_permissions +
user_permissions` keyed by user_id, grouped by scope.

> Backwards-compat: a user who today has the global `admin` role
> still has `PROJECTS_UPDATE` in the union, so every existing scoped
> route passes for them too — no admin lockout.

## Service-layer rules

1. Exactly-one scope per assignment row (CHECK constraint + service guard).
2. Caller-vs-target gate (table above).
3. `super_admin` cannot self-revoke (lockout protection).
4. The last `admin` cannot be revoked (existing rule, ported from `count_users_with_role`).
5. Soft-deleted users' assignments are returned by GET but ignored by the auth middleware's permission load.

## Migration

File: `alembic/versions/<rev>_doc41_scoped_rbac.py` — owned by **monolith**.

Steps (idempotent — every step checks for existence first):

1. CREATE TABLE `user_role_assignments` per the schema above.
2. INSERT a row into `user_role_assignments(user_id, role_id, NULL, NULL)` for every row in `user_roles`. (`user_roles` is left intact during the migration window — phase-out happens in a follow-up.)
3. For every `project_members` row whose `roles` JSON contains "admin" or "member" (or any other role-name the FE may have stored), INSERT a corresponding `user_role_assignments(user_id, role_id_of_<X>_in_project_scope, NULL, project_id)`.
4. INSERT new role rows (`super_admin`, `org_admin`, `project_admin`, `project_member`, `division_member`) and grant their seed permission sets — see "init_db seeds" below.
5. INSERT new permission rows (`USERS_GRANT_SUPERADMIN`, `ACTIVITIES_REQUEST_STATUS_CHANGE`, `ACTIVITIES_APPROVE_STATUS_CHANGE`).
6. Grant every existing-DB row in `roles.name = 'admin'` the new `USERS_GRANT_SUPERADMIN`? **No** — only `super_admin` gets it. Existing `admin` does not.

**Downgrade**: drop `user_role_assignments`. The new permission rows can stay (additive). The seeded roles can stay (no FK from anywhere except the now-dropped table).

## init_db seeds

`RbacRepository.sync_builtin_permissions` extends to:

- Upsert the three new permission codes.
- Upsert five new role rows (`super_admin`, `org_admin`, `project_admin`, `project_member`, `division_member`).
- Seed each role's permission set (see proposed seeds in Decision Log E above; final sets ratified once Q-E is confirmed).
- Promote the existing single bootstrap admin to **super_admin** (one-time, idempotent — only the very first deploy where super_admin is empty).

Per-role seed permission set (proposed):

```
super_admin       = ADMIN_ROLE_PERMISSIONS  +  USERS_GRANT_SUPERADMIN
admin             = ADMIN_ROLE_PERMISSIONS  (i.e. everything except USERS_GRANT_SUPERADMIN)
org_admin         = USERS_READ_ALL, PROJECTS_READ_ALL, PROJECT_MEMBERS_READ,
                    PROJECT_MEMBERS_ADD, PROJECT_MEMBERS_UPDATE, PROJECT_MEMBERS_DELETE,
                    RBAC_ASSIGN  (scope-narrowed in service: only on projects in their vendor)
project_admin     = PROJECTS_READ, PROJECT_MEMBERS_READ, PROJECT_MEMBERS_ADD,
                    PROJECT_MEMBERS_UPDATE, PROJECT_MEMBERS_DELETE, RBAC_ASSIGN,
                    TASKS_*, SUBTASKS_*  (scope-narrowed: only their project; no PROJECTS_UPDATE)
project_member    = PROJECTS_READ, TASKS_READ, TASKS_UPDATE,
                    SUBTASKS_READ, SUBTASKS_UPDATE,
                    COMMENTS_*, ATTACHMENTS_*  (scope: their project)
division_member   = PROJECTS_READ, MILESTONES_READ, ACTIVITIES_READ,
                    TASKS_READ, SUBTASKS_READ,
                    COMMENTS_READ, ATTACHMENTS_DOWNLOAD
                    (scope: their project; READ-ONLY for now — Q4)
                    -- Inbox / status-change approval permissions are
                    -- intentionally NOT seeded here. They land with
                    -- the workbox feature in a future doc, alongside
                    -- the routes that actually consume them.
```

## Risks + open questions (residual — non-blocking)

The four high-leverage questions are answered (see banner). What's
left are minor product calls I'll handle defensively unless you say
otherwise:

- **Bootstrap super_admin promotion**: on first deploy where no row in
  `user_role_assignments` carries `role=super_admin`, auto-promote
  the existing seeded `admin` user (`init_db`'s bootstrap) to
  `super_admin`. Idempotent (no-op once any super_admin exists).
- **`UserResponse` shape**: keep the existing flat `roles: [...]`
  array (legacy FE) AND add a new `roleAssignments: [...]`. FE can
  migrate at its own pace.
- **Cross-monolith scope load cost**: a per-request DB JOIN to load
  scoped permissions costs us one extra query per authenticated
  request. We accept that for now; cache (Redis or in-process LRU
  with a 60s TTL) lands in a follow-up if profiling flags it.
- **Test fixture path**: the new model class is imported in
  `tests/conftest.py` (both repos) so `Base.metadata.create_all`
  picks it up for the in-memory SQLite test DB. No drift-healer
  involvement (that path was retired earlier).
