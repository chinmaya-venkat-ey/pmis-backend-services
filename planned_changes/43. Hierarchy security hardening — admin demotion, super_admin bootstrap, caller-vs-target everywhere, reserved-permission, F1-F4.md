# Doc 43 — Hierarchy security hardening

> **Status: SHIPPED** — landed on `dev` in both repos and deployed
> to the host. The previous role matrix passed 65/65 yet missed
> several real holes (admin holding `users:grant_superadmin`, admin
> able to delete super_admin, admin able to plant the reserved
> permission on other roles, etc.). This doc is the close-out for
> all of those.

This doc covers a coherent set of security hardening fixes that
landed after doc 42:

| # | Sub-change | Repos |
|---|---|---|
| A | `admin` role demoted to `ADMIN_FULL_ROLE_PERMISSIONS` (everything except `users:grant_superadmin`) + boot-time self-heal revoke + role description rewritten without internal doc references. | both |
| B | Bootstrap admin user removed; only `super_admin` is system-bootstrapped now. `admin` is created on-demand by an operator via the API as `super_admin`. | both |
| C | New bootstrap `super_admin` user (separate login from `admin`) created at startup with the doc-41 `user_role_assignments` global row. | both |
| D | Caller-vs-target gate symmetric on grant + revoke (`can_caller_grant` + `revoke_with_lockout_check`). admin cannot grant or revoke `admin` / `super_admin`; only super_admin can. | user-mgmt |
| E | Caller-vs-target gate added to legacy `/users/{id}/roles/{role_id}` POST + DELETE. | user-mgmt |
| F | Lockout pivot: "last active admin" → "last active super_admin" for user soft-delete + status flip + role-assignment revoke. admin is no longer lockout-protected. | user-mgmt |
| G | `super_admin` role row protected from delete / rename / permission mutation (parity with `admin`). | both |
| H | F1 — `can_caller_modify_user(caller, target)` gate on PATCH `/users/{id}`, PATCH `/users/{id}/password`, DELETE `/users/{id}`. admin caller blocked when target holds super_admin. | user-mgmt |
| I | F2 — `users:grant_superadmin` reserved as super_admin-only: refused on direct user-permission grants, refused on PUT / POST role-permission updates targeting non-super_admin roles. | user-mgmt |
| J | F3 — last-super_admin lockout enforced at the user-DELETE service layer (mirrors the existing role-assignment-revoke lockout). | user-mgmt |
| K | F4 — `WARNING` logged at startup when `UNIVERSAL_OTP_ENABLED=true`. | both |
| L | All FE-visible role / permission descriptions + OpenAPI summaries scrubbed of internal doc-number references. Postman collections cleaned the same way. | both + Postman |

## Why this exists

Doc 41 introduced scoped RBAC with five new roles. Doc 42 was the
post-deploy polish (router reorder, OpenAPI hygiene, proxy boundary,
spec-aligned `project_admin` trim, `CORSMiddleware` reorder). Doc 43
is the **security hardening** pass that closes the gap between the
doc-41 design and what the code was actually enforcing.

Two specific things in the live response prompted this:

1. The `admin` role's permission list contained `users:grant_superadmin`
   (because the seed loop unconditionally granted every code in
   `BUILTIN_PERMISSIONS` to admin — the constant
   `ADMIN_FULL_ROLE_PERMISSIONS` defined for the demotion was never
   actually used). Functionally `admin` and `super_admin` were
   identical.
2. The `admin` role description literally read "Built-in superadmin
   role". Wrong twice — admin is not the top tier post-doc-41, and
   it doesn't hold every permission anymore.

A more careful audit then surfaced four classes of attack the role
matrix had missed:

* **F1**: admin could PATCH/DELETE/password-reset any super_admin
  user, taking over their account.
* **F2**: admin could plant `users:grant_superadmin` on a non-locked
  role (e.g. `member`) or grant it as a direct user-permission. Even
  though the current role-name-based grant gate would still block
  the resulting elevation attempt, this is fragile defense — a
  future change to make the gate permission-based would open it up.
* **F3**: the user-DELETE path's lockout only checked against the
  legacy `admin` role, not the new `super_admin`. admin attrition
  was theoretically possible (delete super_admins one by one until
  only the lockout-protected one remained, then the new tier becomes
  trivially compromisable from that user's account).
* **F4**: `UNIVERSAL_OTP_ENABLED=true` is a deliberate dev backdoor;
  silent deploys could carry it into production undetected.

## What's in scope / out of scope

- ✅ Items A–L above.
- ❌ Race-condition lockout (concurrent revokes of the last super_admin
  passing the read-then-write lockout check). Documented as a known
  limitation; real fix requires `SELECT ... FOR UPDATE` row locks
  with serializable isolation. Defer.
- ❌ Rate-limiting login attempts (mitigates F4 partially). Defer to
  a dedicated security doc.
- ❌ `division_member` workbox / approval workflow — unrelated.

## Decision log

| # | Decision | Why |
|---|---|---|
| 1 | Bootstrap `super_admin` (new login) instead of promoting existing `admin` to super_admin | Two clean tiers — admin = day-to-day operations, super_admin = system / RBAC ownership. The bootstrap admin auto-promotion would couple the two and surprise operators who expect `admin` to have always-been admin-tier. |
| 2 | Remove bootstrap admin entirely | Once super_admin exists, the operator should create admin users explicitly. Stops the "who shipped this admin account, and is its password rotated?" pattern. |
| 3 | Caller-vs-target gate is role-name-based, NOT permission-based | Simpler. The reserved-permission guard (item I) keeps the permission-based defense in depth without adding a parallel evaluation path. |
| 4 | Reserve `users:grant_superadmin` strictly to the seeded super_admin role | Defense in depth. Even if the role-name gate is bypassed by a future bug, an attacker still can't get the permission via API. |
| 5 | Drop "last admin" lockout entirely (don't dual-protect) | admin is no longer the protected tier. Keeping the dual lockout would suggest admin is still special. The bootstrap super_admin always exists; admin can be freely demoted now. |
| 6 | F1 hierarchy gate on user mutations is cross-cutting (PATCH + DELETE + password) | Admin holds USERS_UPDATE / USERS_UPDATE_ALL / USERS_DELETE_ALL — they have the permission but should NOT use it on a super_admin target. The gate goes inside the route layer, after `require_permission` but before service-layer dispatch. |
| 7 | `super_admin` role row gets the same delete / rename / permission-update protection as `admin` | The locked-roles set is `{admin, super_admin}`. Both are auto-managed by the seed loop and any manual edit would race on next boot anyway. |
| 8 | Universal-OTP is logged at WARNING, not refused outright | The flag is a legitimate dev-mode break-glass. Refusing startup would surprise dev workflows. WARNING in deploy logs forces ops to flag it during prod cutover. |

## API surface impact

### New `403 Forbidden` paths (admin caller hitting hierarchy boundary)

| Endpoint | Trigger |
|---|---|
| `PATCH /api/v3/users/{id}` | target holds super_admin |
| `PATCH /api/v3/users/{id}/password` | target holds super_admin |
| `DELETE /api/v3/users/{id}` | target holds super_admin |
| `POST /api/v3/users/{id}/permissions/{code}` | code is `users:grant_superadmin` (any caller below super_admin) |
| `PUT /api/v3/roles/{id}/permissions` | request includes `users:grant_superadmin` and the role isn't `super_admin` |
| `POST /api/v3/roles/{id}/permissions/{code}` | code is `users:grant_superadmin` and role isn't `super_admin` |
| `POST /api/v3/users/{id}/roles/{role_id}` (legacy) | admin caller, target role is `admin` or `super_admin` |
| `DELETE /api/v3/users/{id}/roles/{role_id}` (legacy) | same |
| `POST /api/v3/users/{id}/role-assignments` | admin caller, target role is `admin` or `super_admin` (covered before this doc) |
| `DELETE /api/v3/users/{id}/role-assignments/{aid}` | admin caller revoking an admin / super_admin assignment (NEW gate added in this doc) |

### New 422 lockout message

| Endpoint | Trigger | Message |
|---|---|---|
| `DELETE /api/v3/users/{id}` | target is the last live super_admin | `Cannot delete the last active super_admin. Promote another user to super_admin first.` |
| `PATCH /api/v3/users/{id}` (status=inactive) | target is the last live super_admin | `Cannot deactivate the last active super_admin. Promote another user to super_admin first.` |
| `DELETE /api/v3/users/{id}/role-assignments/{aid}` | target row is the last global super_admin assignment | `Cannot revoke the last global super_admin — at least one super_admin must remain to grant the role to others.` |

### Bootstrap behaviour (both repos)

* On every boot:
  - RBAC seed runs (admin/super_admin roles, all five doc-41 sub-roles, every built-in permission).
  - Self-heal: any pre-existing `users:grant_superadmin` grant on `admin` is revoked.
  - super_admin user created if missing (login + password from `BOOTSTRAP_SUPERADMIN_*` env vars; defaults `super_admin` / `superadmin123`).
  - super_admin user receives a global `user_role_assignments` row for `super_admin` if missing.
* The previous boot-time admin auto-creation is GONE. Existing admin user records on the deployed DB are untouched.

## Lessons learned

- **Self-heal is a load-bearing pattern.** When a seed loop only ADDS,
  any code-level revoke takes effect only on fresh DBs. Always pair
  a seed-list change with a one-line revoke for the deprecated entry.
- **Role-name vs permission-code gates trade simplicity for
  flexibility.** We kept role-name gates here — simpler — and added a
  separate reserved-permission guard as defense in depth. If a
  future role wants delegated grant-superadmin authority, we'd
  switch to permission-based gates centrally.
- **Lockout protections shift as tiers evolve.** Pivoting "last
  admin" → "last super_admin" required touching three different
  files (delete service, update service, role-assignment revoke).
  Centralising lockout logic in a `LockoutGuard` class would prevent
  drift; doable in a follow-up.
- **OpenAPI / response strings leak internal doc numbers.** Easy to
  scatter `(doc 41)` markers when you're heads-down on a feature.
  Worth a CI lint that flags `[Dd]oc \d+` in route summaries /
  descriptions / role descriptions.
- **Bootstrap accounts deserve their own threat model.** A
  hard-coded `admin/admin123` carried into prod is the canonical
  "default credentials" CVE — removing the auto-create plus
  requiring an explicit super_admin promotion path makes the system
  harder to ship insecurely.

## Round 2 — peer-takeover + self-deactivate hardening (G1 / G2 / G3)

A walkthrough on live v18 surfaced three holes that the F1-F4 round
did not close. The original boundary work focused on
admin-vs-super_admin (vertical) and never explicitly modelled
super_admin-vs-super_admin (horizontal). Once two SAs are on the
system the missing checks become exploitable.

### Holes found by walkthrough

| ID | Hole | Why it's bad |
|---|---|---|
| G1 | A user (any tier) could deactivate their **own** account via `PATCH /users/{me}` `status=inactive`. | Symmetric with self-delete. A super_admin self-deactivating loses login mid-session. The last-SA lockout fires only when the target is the **single** SA — with two SAs, self-deactivate sails through. |
| G2 | A super_admin could change **another** super_admin's password via `PATCH /users/{peer}/password`. | Account takeover with no audit-trail signal. The hierarchy gate previously only blocked admin → super_admin; peer-on-peer was unguarded. |
| G3 | A super_admin could DELETE **another** super_admin directly. | Same takeover surface as G2. Lockout (F3) fires only when target is the last SA; peer-deletion of one of two SAs leaves the actor as sole SA — exactly the escalation we want to prevent. |

### Fixes

| Guard | File | Change |
|---|---|---|
| G1 | `app/api/v3/users/services/update.py` | Top-of-function check: `if status == "inactive" and is_self → 403 "Cannot deactivate your own account."`. Sits before the existing self-demote and last-SA-lockout guards. Tier-agnostic. |
| G2 + G3 | `app/api/v3/role_assignments/services.py` | New helper `_user_holds_super_admin(db, user_id)`. Extended `can_caller_modify_user(db, caller_id, target_user_id, *, op="patch")` with an `op` parameter; when `op="destructive"` the gate **also** refuses super_admin → super_admin. Existing `op="patch"` behaviour unchanged (peer SA can still PATCH non-status fields on a peer — needed for promote/demote workflows). |
| G2 | `app/api/v3/users/routes.py` — `update_user_password` handler | Now calls `can_caller_modify_user(..., op="destructive")` before invoking the service. |
| G3 | `app/api/v3/users/routes.py` — `delete_user` handler | Same — `op="destructive"` on the pre-check. |

The escape hatch for legitimate cases: an SA who genuinely needs to
delete or password-reset another SA must first **revoke that user's
super_admin role assignment** (which goes through the symmetric
caller-vs-target grant gate from F1). Once demoted, the destructive
op proceeds normally.

In `tests/test_doc43_hierarchy_security.py`, three new classes:

- `TestSelfDeactivateBlocked` — super_admin can't self-deactivate
  even when another SA exists; admin can't self-deactivate.
- `TestPeerTakeoverPasswordChange` — SA can change own password and
  a lower-tier user's password, but not another SA's; demoting first
  unblocks it.
- `TestPeerTakeoverDelete` — symmetric: SA can't DELETE another SA;
  demoting first unblocks it.

The existing F3 test `test_can_delete_super_admin_when_others_exist`

In `tests/test_users.py`, `TestAdminProtectionGuards` adjusted:

- `test_admin_can_be_deactivated_post_doc42b` renamed to

- `test_cannot_deactivate_last_active_super_admin` rewritten as

### Lessons added

- **Boundary tables are only as honest as the probes that filled
  them.** Round-1 had inferred-from-code rows that masked these
  three holes; the walkthrough on live v18 produced the
  observed-by-probe table that flushed them out. Going forward,
  matrix rows that are not exercised end-to-end against a live
  service should be marked clearly so they aren't mistaken for
  verified.
- **"Hierarchy" needs a horizontal axis too.** "Lower tier can't
  touch higher tier" closes the vertical attack; "peer can't
  takeover peer on destructive ops" closes the horizontal one.
  Both need explicit guards — neither implies the other.
- **Lockout ≠ self-action guard.** They overlap when there's only
  one of the protected tier. Once you allow more than one of the
  protected tier, only the explicit self-action guard catches
  self-takeout.
