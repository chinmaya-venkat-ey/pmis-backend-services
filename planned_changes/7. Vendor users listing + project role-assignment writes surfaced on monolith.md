# Doc 7 — Vendor-users listing + project role-assignment writes surfaced on the monolith

> **Status: SHIPPED** — user-mgmt side landed in `bc0839b`-area
> commits; monolith side landed as a separate set of thin forwarders.

Cross-cutting move that adds three routes to monolith :8000 by
forwarding them to user-mgmt's existing handlers, so the FE never
needs a direct :8001 call for these:

| # | Sub-change |
|---|------------|
| 1 | New `GET /api/v3/vendors/{vendor_id}/users` here — flat list of users mapped to a vendor (via `users.vendor_id`). Authz: `users:read_all` (admin) OR `org_admin` of this vendor. Pagination + status + admin-tier exclusion from the existing `list_users` service. |
| 2 | The monolith side now exposes thin forwarders for `POST /projects/{id}/role-assignments`, `DELETE /projects/{id}/role-assignments/{aid}`, and `GET /vendors/{id}/users`. They `await proxy_or_503(...)` and the real logic stays here. |

---

## Why this exists

The FE needs to render "users assigned to this vendor" from the
project-opened User Management view, which is a `:8000` surface. The
listing query (users filtered by vendor_id, joined to role
assignments) naturally belongs in user-mgmt because the data is
user-mgmt-owned. Rather than duplicate the join or call
`:8001` from the FE, we surface the route on the monolith and forward.

Companion: the existing scoped-role POST and DELETE under
`/projects/{id}/role-assignments` had no monolith presence at all —
hitting `:8000` returned 404 instead of forwarding. The thin
forwarders (in monolith doc 48) close that hole.

## What's in scope / out of scope

- ✅ `GET /vendors/{vendor_id}/users` (this repo)
- ✅ Thin forwarders on monolith — body, query, Authorization
  forwarded as-is; upstream response bubbled back unchanged
- ❌ Cross-vendor user search (out of scope — vendor-scoped only)
- ❌ Vendor-side role-assignment writes (those live on
  `/users/{id}/role-assignments` and are unchanged)

### Lessons learned

- The "monolith owns the URL namespace, user-mgmt owns the logic"
  conflict naturally resolves to thin forwarders. The cost is one
  HTTP hop (~8ms locally), measured negligible at single-user load.
- Forwarder handlers must be `async def` and `await proxy_or_503` —
  the now-async proxy plumbing returns a coroutine.
