# Doc 8 — User.division validated against the shared divisions master table

> **Status: SHIPPED** — landed on `dev` in this repo, monolith mirror,
> and project-management mirror. Cross-repo coordination — see
> [monolith doc 49](../../PMIS-OpenProject/planned_changes/49.%20Division%20master-table%20validation%20on%20User%20and%20Activity%20ownerDivision.md)
> for the cross-cutting plan.

`POST/PATCH /users` and `POST/PATCH /users/{id}` now reject any
`division` value that isn't an active row in the shared `divisions`
master table. Previously: pre-doc-5-era code enforced a strict
hardcoded `tmd1`/`tmd2`/`others` enum; mid-flight an interim
loosening removed the enum entirely (accepting any string); doc 8
replaces that with a proper master-table lookup so admins can add
new divisions via the monolith's catalog API and they become
assignable here without a code change.

---

## Why this exists

The hardcoded enum was inflexible — adding a new division required a
code release. The interim "accept any string" was too loose — users
were being created with arbitrary garbage division values. Master-
table validation closes both: built-ins continue to work (init_db
seeds them); admin-added codes via `POST /api/v3/master/divisions/
create` on the monolith are picked up automatically; soft-disabled
rows are rejected (active-only check).

## What's in scope / out of scope

- ✅ Lookup against `divisions.code WHERE active = true` on create
  and update
- ✅ Built-in models `tmd1`/`tmd2`/`others` continue to work because
  init_db seeds them in the same `divisions` table
- ✅ `divisionOther` coupling preserved — when `division == 'others'`,
  `divisionOther` must be a non-empty label
- ❌ `divisionOther` itself is not catalog-validated — it's free text
  on the user row
- ❌ Auto-create-on-write of new division rows (the pre-doc-20
  behaviour where free-text owner labels mirrored into a divisions
  row) is NOT brought back

---

## Schema

No schema change in this repo. The `divisions` table is owned by the
monolith. This repo adds a **read-only ORM mirror**:

```
app/infrastructure/db/models/division.py (NEW — read-only)
  id              INTEGER PK
  code            VARCHAR(64) UNIQUE NOT NULL  (lowercased)
  label           VARCHAR(255) NOT NULL
  is_builtin      BOOLEAN NOT NULL
  requires_other  BOOLEAN NOT NULL
  active          BOOLEAN NOT NULL
  created_at, updated_at  UtcDateTime
```

The model only declares the columns user-mgmt reads. doc-36 columns
(`email`, `phone_number`) exist in production but aren't declared
here. `Base.metadata.create_all` builds the table inside in-memory
SQLite test DBs so the test fixture can seed built-ins.

`services/create.py` and `services/update.py` inside the existing

### Lessons learned

- The shared-DB pattern means user-mgmt reads tables it doesn't
  *own*. A minimal read-only model (only the columns we touch) keeps
  the coupling explicit and the schema-drift surface small.
- `divisionOther` is *the* place we'd want to evolve the model next.
  Right now it's free text; the user explicitly deferred decisions
  about it. When that's revisited, it likely becomes its own catalog
  or a structured tag list.
