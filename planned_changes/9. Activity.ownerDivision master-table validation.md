# Doc 9 — Activity.ownerDivision master-table validation

> **Status: SHIPPED** — mirror of [monolith doc 49](../../PMIS-OpenProject/planned_changes/49.%20Division%20master-table%20validation%20on%20User%20and%20Activity%20ownerDivision.md).
> The cross-cutting plan lives in monolith doc 49; this is the
> project-mgmt slice.

Replaces the strict hardcoded `tmd1`/`tmd2`/`others` enum check on
`Activity.ownerDivision` with a master-table lookup against the
shared `divisions` table. Admins can add new division codes via
`POST /api/v3/master/divisions/create` on the monolith and they
become assignable immediately on activities here too.

| File | Change |
|---|---|
| `app/api/v3/activities/schemas.py` | `_validate_division_code` now only normalises (strip + lowercase + non-empty). |
| `app/api/v3/activities/services/create.py` | After binding, call `DivisionRepository(db).is_known_code(owner_division)` and 422 on miss. |
| `app/api/v3/activities/services/update.py` | Same check on PATCH (only when `owner_division` is supplied non-empty). |
| `tests/conftest.py` | `db_engine` seeds `tmd1`/`tmd2`/`others` into the in-memory `divisions` table for tests. |

`Project.owner` was already DB-extended (validated against the live
table with a hardcoded fallback for empty-DB scenarios) — unchanged.

`concernedDivision` is the list field on activities and already
accepted free text — unchanged.
